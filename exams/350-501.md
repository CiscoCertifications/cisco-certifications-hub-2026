## 1. Exam Overview & Candidate Profile

The **Cisco 350-501 SPCOR** exam tests a candidate's knowledge of implementing core service provider network technologies, including core architecture, services, networking, automation, quality of services, security, and network assurance. Passing SPCOR earns the **Cisco Certified Specialist - Service Provider Core** credential, satisfies the core requirement for **CCNP Service Provider**, and qualifies candidates to attempt the **CCIE Service Provider** practical lab.

### Target Candidate Profile & Roles
* **Service Provider Core Network Engineer**
* **Carrier IP/MPLS Network Architect**
* **ISP Operations Specialist**
* **Prerequisites:** No formal prerequisites. 3–5 years administering service provider routing environments (Cisco IOS XR and XE) is typical.

## 4. Scenario-Based Technical Practice Questions

### Scenario 1: Segment Routing Prefix SID Allocation
**Question:** In a Cisco IOS XR carrier network running Segment Routing over MPLS (SR-MPLS), the Segment Routing Global Block (SRGB) is defined as `16000` to `23999`. Router PE-1 has a loopback IP of `10.0.0.1/32` and is configured with Prefix SID index `101`. What MPLS label value will adjacent P-routers use to forward traffic along the shortest path toward PE-1's loopback?

* A. 101
* B. 16000
* C. 16101
* D. 23999

**Correct Answer:** **C**

**In-Depth Architectural Explanation:**
* **Why C is correct:** In SR-MPLS, a **Prefix SID** is represented as an index offset relative to the base of the Segment Routing Global Block (SRGB). The formula to calculate the active MPLS transport label is:
  $$\text{Label} = \text{SRGB\_Base} + \text{SID\_Index}$$
  Here: $16000 + 101 = 16101$. Every router in the IGP domain installs label 16101 into its Forwarding Information Base (FIB) pointing toward PE-1.
* **Distractor Analysis:**
  * Option A (101) is the raw SID index, not the calculated MPLS label.
  * Option B (16000) is the base label of the SRGB.
  * Option D (23999) is the upper boundary of the allocated SRGB range.

### Scenario 2: MPLS L3VPN Route Distinguisher (RD) vs. Route Target (RT)
**Question:** A Service Provider provides MPLS L3VPN connectivity for two enterprise customers who both use overlapping private IPv4 addressing (`10.1.1.0/24`). Which BGP attribute enables the Provider Edge (PE) router to maintain unique, non-overlapping prefixes inside the MP-BGP table?

* A. Route Target (RT) extended community
* B. Route Distinguisher (RD)
* C. BGP Community `no-export`
* D. Site-of-Origin (SOO) attribute

**Correct Answer:** **B**

**In-Depth Architectural Explanation:**
* **Why B is correct:** A **Route Distinguisher (RD)** is an 8-byte value prepended to an IPv4 prefix (converting a 32-bit IPv4 address into a unique 96-bit VPNv4 address, e.g., `65000:100:10.1.1.0/24`). This ensures that BGP can store and advertise identical overlapping IP prefixes from different customers without collision in the VPNv4 table.
* **Distractor Analysis:**
  * Option A (Route Target) is an extended BGP community used to control which VRF routing tables import and export routes, not to make the address globally unique in the BGP table.
  * Option C (`no-export`) prevents routes from being advertised outside the local AS.
  * Option D (SOO) prevents routing loops in multi-homed BGP sites.

### Scenario 3: BGP Route Reflector and Loop Prevention
**Question:** In an internal BGP (iBGP) mesh with BGP Route Reflectors (RR), how does a Route Reflector prevent routing loops when reflecting routes to its clients and other Route Reflectors?

* A. By prepending its own AS number to the AS-Path attribute.
* B. By using the `ORIGINATOR_ID` and `CLUSTER_LIST` BGP path attributes.
* C. By resetting the MED attribute to 0 on all reflected routes.
* D. By blocking all routes learned via eBGP.

**Correct Answer:** **B**

**In-Depth Architectural Explanation:**
* **Why B is correct:** Route Reflectors bypass the standard iBGP split-horizon rule (which prohibits advertising an iBGP-learned route to another iBGP peer). To prevent loops:
  * **ORIGINATOR_ID:** A 4-byte attribute created by the first RR carrying the BGP Router ID of the originating router in the local AS. If an update is received with the local router's own Router ID as the ORIGINATOR_ID, the update is dropped.
  * **CLUSTER_LIST:** An ordered list of Cluster IDs through which the update has passed. If an RR sees its own Cluster ID in the list, it recognizes a loop and discards the update.
* **Distractor Analysis:**
  * Option A is invalid; AS-Path is only modified when crossing eBGP boundaries, never within iBGP.
  * Option C (MED) influences inbound multi-homing path selection, not loop prevention.
  * Option D is incorrect; Route Reflectors routinely reflect eBGP-learned prefixes into the iBGP mesh.

### Scenario 4: Cisco IOS XR Process Architecture and High Availability
**Question:** On a Cisco ASR 9000 running 64-bit Cisco IOS XR, what architectural mechanism ensures that routing protocols can restart independently without reloading the operating system kernel or impacting data forwarding in the hardware ASICs?

* A. Microkernel architecture with dedicated user-space processes and Non-Stop Forwarding (NSF).
* B. Monolithic software image with integrated fast-boot memory paging.
* C. Dual-active route processor clustering with active-active CLI sync.
* D. Hardware virtualization running individual dockers for every physical interface.

**Correct Answer:** **A**

**In-Depth Architectural Explanation:**
* **Why A is correct:** Cisco IOS XR uses a modular **microkernel** architecture (based on QNX/Linux). Each protocol (BGP, OSPF, LDP) and management subsystem runs as an isolated memory-protected user-space process. If a protocol process crashes or is restarted, the microkernel restarts only that specific process, while the forwarding plane continues routing line-rate traffic uninterrupted via CEF and **Non-Stop Forwarding (NSF)**.
* **Distractor Analysis:**
  * Option B describes legacy monolithic Cisco IOS, where a process crash crashed the entire router.
  * Option C is incorrect; route processors operate in active-standby redundancy, not active-active CLI sync.
  * Option D is false; interfaces are managed by line-card NPUs and driver processes, not individual Docker containers.

### Scenario 5: EVPN All-Active Multi-Homing and Split-Horizon
**Question:** In a BGP EVPN network with Ethernet Segment Identifier (ESI) all-active multi-homing, how do PE routers prevent Broadcast, Unknown Unicast, and Multicast (BUM) frames sent by a multi-homed CE from being looped back to the same CE over the redundant PE link?

* A. By disabling MAC learning on all trunk ports.
* B. By using an ESI-based Split-Horizon MPLS label advertised via EVPN Route Type 1 (Auto-Discovery per ES).
* C. By blocking the redundant link using Rapid Spanning Tree Protocol (RSTP).
* D. By rewriting the source MAC address to the PE switch's system MAC.

**Correct Answer:** **B**

**In-Depth Architectural Explanation:**
* **Why B is correct:** In EVPN all-active multi-homing (RFC 7432), an Ethernet Segment is assigned an **ESI label** via EVPN Route Type 1 (Ethernet Auto-Discovery per ES route). When PE1 receives a BUM frame from CE1, it encapsulates it with the transport label and the specific ESI label before forwarding it across the core. When redundant PE2 receives the packet, it inspects the ESI label; recognizing that the packet originated from the same Ethernet Segment to which PE2 is attached, it drops the packet instead of sending it back to CE1 (ESI split-horizon filtering).
* **Distractor Analysis:**
  * Option A is false; EVPN relies on control-plane MAC learning.
  * Option C defeats the primary purpose of all-active multi-homing (eliminating Spanning Tree blocking).
  * Option D alters Layer 2 payload integrity and breaks client connectivity.
